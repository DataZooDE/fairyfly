# BP agent and fairyfly timing, 2026-10-29

Environment: Bigfox A4H, client 001, SAP GUI on Windows, fairyfly Release CLI, one attached session. The workflow opened transaction BP, read its editable fields, opened Create Organization, read its editable fields, filled `timing-probe@example.invalid`, cancelled, read the confirmation, discarded the unsaved change, and verified the return to Maintain Business Partner. Each run ended with SAP reporting `Changes were not saved`. No business partner was created or edited persistently.

## End-to-end comparison

| Execution | Agent calls to fairyfly | fairyfly processes | End-to-end wall time | Sum of fairyfly process wall times | Sum of `metadata.duration_ms` |
| --- | ---: | ---: | ---: | ---: | ---: |
| Nine agent-selected steps | 9 | 9 | 55.0 s | 5.06 s | 2.87 s |
| Nine separate CLI processes inside one agent tool call | 1 | 9 | 8.26 s | 6.60 s | 3.79 s |
| One `fairyfly batch` process with nine steps | 1 | 1 | 6.17 s | 6.17 s | 4.71 s |

The agent-selected run was timed from 16:19:13 to 16:20:08 UTC. Its roughly 50 seconds outside CLI process time includes model reasoning, tool routing, and response handling; these components were not timed separately. The agent received concise result summaries in this comparison, so a client that sends full screen payloads to the model can incur more processing time. The same static batch was repeated once at 6.20 s wall time.

SAP execution varied between runs. The first BP field read took 140 ms, 1,283 ms, and 1,788 ms, respectively. The 2.1 second difference between the separate-process and batch runs is therefore a useful indication, not a stable process-startup estimate. The much larger agent-call gap is clear in this sample.

## Call and response costs

In the agent-selected run, starting BP took 792 ms, opening Create Organization 567 ms, filling the email field 31 ms, and cancelling plus discarding 889 ms in fairyfly's command metadata. The initial and final BP field reads were 140 ms and 123 ms; the create-form field read was 282 ms. A prior BP read with tab expansion took 3,076 ms, while compact reads of the visible screen with `--no-tabs` took 129–133 ms. Those reads used different filters, so the comparison is directional.

For the 46 editable fields on Create Organization, response sizes were:

| Format | Characters | Limitation |
| --- | ---: | --- |
| Compact JSON | 61,025 | Includes long absolute IDs and repeated hierarchy data |
| TOON with `--compact` | 55,064 | Still repeats long IDs |
| Markdown with IDs | 27,136 | Keeps empty fields and technical IDs |
| Compact Markdown | 5,148 | Hides empty fields and IDs needed to fill the form |

The nine-line CLI batch returned 71,452 characters. MCP `gui_batch` similarly concatenates every step's text result. Batching therefore removes round trips but can still give the model a large response.

## Improvement candidates

1. Add a compact result mode to `gui_batch`: return status, selected values, errors, and per-step timing by default; retain full step output only when explicitly requested. Keep audit records and error details available.
2. Let a batch bind fields found by an earlier step and refer to them by short names in later steps. Current CLI batch is static and cannot substitute results; MCP `gui_batch` also executes a fixed item list. Use screen identity checks and fail on ambiguous field names or a changed screen.
3. Support guarded flow steps for common dialogs and outcomes: assert the expected title/status, branch on a known popup, and stop before any unrequested Save. This would allow an agent to submit a whole routine while fairyfly checks each transition.
4. Return short field references for the current screen and avoid repeating long absolute IDs in the model-visible response. Preserve a way to request full IDs for diagnostics.
5. Prefer targeted reads and the existing multi-field `gui_element_fill` for current workflows. Screen reads across inactive tabs should be requested only when needed; measure and optimize tab expansion separately.
6. Add per-phase timing and response-size telemetry to MCP results: queue, SAP action/wait, screen collection, formatting, serialization, and total request time. Agent clients can then add model latency, tool-call count, and token usage.

Existing primitives: CLI `batch` runs sequential commands in one process but cannot use earlier results as later arguments. MCP `gui_batch` accepts up to 20 calls in one round trip and concatenates their text responses (`src/mcp/dispatcher.cpp`). `gui_element_fill` already accepts up to 50 fields and an optional `then_key` (`docs/MCP.md`).

This exercise did not time a persisted BP creation, an existing partner's email change, or Save. Those need a designated disposable test partner and creation identity.
