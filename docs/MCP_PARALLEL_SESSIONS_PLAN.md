# Parallel SAP GUI Sessions over MCP Implementation Plan

This plan describes how Fairyfly runs calls to different SAP GUI sessions concurrently through one tray MCP endpoint. It consolidates the initial design and two independent Claude Opus 5.5 reviews, including a security and enterprise deployment review. The owner-allowlisted HTTP path routes established-session calls and disconnect through private workers and per-session FIFO lanes. Attach, launch, and login run through coordinated control paths with live owner and token checks. The primary design is one interactive Windows account running one Fairyfly tray and multiple SAP GUI sessions, which may be logged in as different SAP users. Password and SSO/SNC configuration is covered in [MCP_SAP_AUTHENTICATION.md](MCP_SAP_AUTHENTICATION.md).

## Current behavior

`fairyfly mcp --http --tray` runs in one logged-on Windows desktop session. http.sys accepts concurrent HTTP requests. Without an owner SAP identity allowlist, [`CallExecutor`](../src/include/mcp/call_executor.h) still executes all tool work on one COM STA thread through one shared [`CommandHandler`](../src/mcp/run_mcp.cpp). With an owner allowlist, established-session calls use private worker processes and per-session lanes; global control commands remain on the tray executor. The CLI [`CommandRegistry`](../src/mcp/dispatcher.cpp) holds a process-wide mutex only within each process.

Saved numeric `connection` IDs map to SAP GUI session IDs and server session keys. A tool can target a particular saved session with `connection`. HTTP does not issue an `Mcp-Session-Id`; the last successful attach or launch is a sticky default **per token** unless a server default takes precedence. Two clients using the same token share that default. Clients that target the same SAP GUI session share its screen state even when their MCP calls are separately authenticated.

## Intended behavior

- Calls to one SAP GUI session execute in order, with no overlap inside that session.
- Calls to different SAP GUI sessions can overlap when SAP GUI itself permits it. A busy session must not unnecessarily stall another.
- Every call is routed to the intended live session, including after windows close or session indices change. A stale saved ID fails instead of silently selecting another session.
- Token restrictions, read-only guards, audit records and cancellation behavior remain correct under concurrency.
- One interactive Windows account can use several SAP GUI sessions in parallel through one endpoint, including sessions logged in as different SAP users. Separate tokens identify MCP clients or agents and must be bound to the SAP identities each is allowed to use. Separate Windows accounts and endpoints are an optional stronger boundary when independent Windows credential custody is required.

## Authentication and session ownership

There are two separate authentications. The HTTP caller presents a Fairyfly bearer token, which identifies an MCP client credential and supplies scopes and restrictions. The SAP GUI session is authenticated to SAP through a normal interactive logon or Fairyfly's existing launch/login flow using credentials stored in the Windows Credential Manager. The MCP token is never a SAP password and does not itself log in to SAP. All workers run as the tray's Windows desktop user; separate MCP tokens do not create separate Windows identities. The endpoint allowlist specifies which SAP system/client/user identities this tray may expose; each token also needs its own SAP identity restriction when different clients must see different SAP users.

**Current code gives owner-mode HTTP clients exclusive leases for session-changing actions, while reads remain shared.** The endpoint SAP identity allowlist filters session discovery and established calls; the token's exact `--sap-identity` grants narrow that list for each client. Legacy unbound tokens fail closed when the endpoint allows multiple SAP identities. A saved numeric `connection` ID is a target, not a secret or capability. `--connections` restricts SAP Logon/connection *names*, which may be shared by different SAP users. A multi-identity endpoint can use atomic `gui_session_launch` with `login:true` for password logon or a token-bound prelogin window followed by `gui_session_login` from the same token. That token can also close its unfinished window while its 15-minute binding is valid. SSO launches must finish with a verified, token-authorized SAP user. SAP roles remain the primary limit on what that SAP user can do; Fairyfly read-only and T-code guards add another layer.

Recommended single-owner contract:

1. Give each remote client or agent its own short-lived token with only the required scopes. Treat the token as a bearer credential, not proof of a particular person or MFA event. Sharing a token deliberately shares that client identity. Token rotation currently creates a **new token ID** in [`TokenStore::issue`](../src/auth/token_store.cpp), so leases keyed by token ID expire on rotation; any future binding keyed by token ID must be migrated explicitly.
2. Configure the endpoint's allowed SAP identity or identities locally and bind each client token to its authorized `SID/CLIENT/USER` identity or explicit set of identities. When an endpoint permits more than one SAP identity, reject an unbound token for owner-mode session calls and discovery. Check the intersection of endpoint and token identities against live SAP system, client and user before listing, attaching, logging in, reading or acting. Fail closed when those facts are unavailable or change. A saved numeric connection ID is only a lookup handle; verify its live session key and cache generation before use. A distinct SAP account needs an explicit allowlist entry and token grant, not automatic discovery.
3. Keep token scopes, `--connections`, `--system`, read-only and T-code restrictions as additional per-client limits. Restrict remote launch/login and stored credential *names* where needed, but recognize that all credentials in this Windows user's Credential Manager remain accessible to processes of that Windows user. A token must not make an unapproved SAP identity visible by launching or attaching it.
4. Use a session lease to coordinate the owner's agents during multi-step writes. Another client token can be granted a lease only for a session already allowed to this endpoint. Read-only clients can share a session if their calls do not change its screen; navigation still changes screen state and needs coordination or stale-screen checks.
5. Recheck the token's current status, effective policy, live SAP identity and lease when a queued request begins, not just when HTTP receives it. Queued HTTP jobs now force a fresh token-store read at execution start and use the refreshed principal; revocation after that point cannot stop an in-flight COM action. Remove idle leases promptly on revocation where possible.
6. Filter `gui_session_list`, `gui_connection_list` and diagnostics to the configured owner's allowed identities and the token's narrower rules before shaping the response. A disallowed ID returns a non-enumerating denial. The server-wide default and single-connection fallback must never route a call to a disallowed session.

This is **MCP-level control among remote clients of one tray**, not an operating-system security boundary. Another process running as the same Windows user can access that user's SAP GUI and Credential Manager independently of Fairyfly. If independent Windows credential custody is required, run separate interactive Windows accounts and Fairyfly endpoints. Binding tokens to SAP identities can separate MCP visibility and actions, provided the tokens stay private; binding tokens to `ses[n]` alone does not establish SAP identity.

## Minimal enterprise deployment profile

Start with one endpoint for one approved owner on a managed Windows desktop or VDI. Keep the existing http.sys listener, tray, bearer tokens and setup workflow; do not require a database, directory integration, reverse proxy or new Windows service for the first release. Use local stdio where the MCP client runs in the same desktop session. For remote clients use HTTPS and a certificate issued by the organization's PKI where available; Fairyfly already accepts `--cert-thumbprint`. Use `mcp setup --user DOMAIN\user` to reserve the URL for the actual tray account when an administrator performs setup. A deployment tool running as SYSTEM must supply that user explicitly; the default current-user SID would be SYSTEM.

Keep each endpoint under the intended interactive Windows account. Existing `mcp setup` and tray autostart should be tested against the organization's UAC, RDP/VDI, screen-lock, firewall and endpoint protection policies. A shared RDS host requires a separate listener configuration per account and careful treatment of loopback: another logged-on user can reach `127.0.0.1`, and a local tunnel can make remote traffic appear to come from loopback. Owner mode requires bearer authentication even on loopback and rejects `--insecure-no-auth`; `server.allow_ip_include_loopback` or `--allow-ip-include-loopback` now makes the server IP allowlist apply there too when configured. Hosting several user endpoints on one port with separate URL paths would require changes to the currently fixed `/mcp` route and setup; do not assume it works today. Separate VDI hosts or distinct reserved ports are simpler for an initial rollout.

Use SAP-side authorization as the primary business access control: grant only the required roles and, where the SAP landscape supports it, enable scripting only for approved SAP users through `sapgui/user_scripting_per_user` and `S_SCR`. SAP documents these controls in its [GUI Scripting Security Guide](https://help.sap.com/docs/sap_gui_for_windows/1f190e2f59db43e192cba638ea29870b/76d8d2b932ce4e71b91c313d818a51f2.html). Prefer the organization's approved SAP SSO where available so Fairyfly need not store a SAP password. Confirm SAP account type, licensing, session limits and audit requirements with SAP Basis/security; do not assume a technical service account may use an interactive GUI.

For managed rollout, package and sign the binary, install it in an administrator-controlled directory, and document its network listener, COM automation and Credential Manager access for application allowlisting. `mcp doctor` should report certificate expiry/binding, URL reservation for the tray SID, effective firewall access, desktop availability and audit health. Certificate renewal needs a documented rebind step because an http.sys TLS binding uses a certificate thumbprint. Send existing JSONL audit files to the organization's log collector or add an optional Windows Event Log sink; MCP audit records now carry the token issuance ID alongside request ID, peer address and SAP identity.

Direct LDAP password authentication adds deployment cost and should not be required. Add enterprise SSO or OIDC only when real human callers need centrally managed identity, MFA or Conditional Access; it is not necessary for client credentials used by one approved endpoint owner. Keep the identity provider integration optional and separate from the parallel-session scheduler.

## Optional Windows service front end

A Windows service can own the stable HTTPS endpoint, health reporting and reconnect logic, but it cannot run the SAP GUI scripting worker itself. Windows services run in Session 0, separate from the interactive SAP GUI desktop. Microsoft recommends a separate process in the logged-on user's session with IPC to the service for this pattern: [Interactive Services](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services). Running the service under the same Windows account as SAP GUI does not move it onto that account's interactive desktop.

For the smallest useful service design, keep one hidden, unelevated Fairyfly **desktop agent** per endpoint owner. Start it at that user's logon with the existing per-user autostart mechanism or a managed scheduled task; make the tray icon optional. The service runs under a low-privilege service identity, listens through http.sys and forwards MCP requests and responses to its configured agent over a local, access-controlled IPC channel. The agent retains SAP COM, the handler, current token store in that user's Credential Manager, and live SAP policy checks. The service verifies the agent's configured Windows SID and session on every connection. Client bearer tokens remain mandatory, including on loopback. When the agent is absent or its desktop is unusable, return an explicit `SESSION_UNAVAILABLE` or `DESKTOP_UNAVAILABLE` response; never start a second agent in Session 0 or claim that a booted service means SAP is available.

Keeping token authentication in the desktop agent avoids migrating user-scoped token secrets to a machine-scoped store for the first release. The service should forward the HTTP request without weakening Host, Origin, peer-address or token checks; the real peer address must be passed as a service-authenticated fact, never trusted from a client header. SSE, cancellation and timeouts need end-to-end forwarding. A later service-owned authenticator is possible, but requires deliberate token migration and a second authorization boundary. Avoid `WTSQueryUserToken` and `CreateProcessAsUser` in the first version: that would require a highly privileged launcher and more complex logon-session lifecycle. Microsoft documents `WTSQueryUserToken` as requiring LocalSystem plus `SE_TCB_NAME`: [WTSQueryUserToken](https://learn.microsoft.com/en-us/windows/win32/api/wtsapi32/nf-wtsapi32-wtsqueryusertoken).

The service is an operations improvement, not an unattended-SAP solution. A Windows user still has to be logged on to an interactive desktop, with SAP GUI open and scripting enabled. Locking, RDP disconnects, logoff, GUI-wide dialogs and screenshots retain their existing limitations. Keep direct tray/console HTTP mode for small or single-user deployments; enable the service front end only where IT requires Service Control Manager lifecycle, a machine-managed listener or centralized health checks.

## Implementation status (2026-10-04)

The owner-allowlisted tray HTTP path now routes established-session tools through private Windows worker processes and bounded per-session FIFO lanes. The tray performs owner and token checks at admission and dequeue; the worker verifies the saved connection generation, SAP system/client/user and session identity before each action. Token status and leases are checked again at the private IPC boundary. Same-session calls remain ordered, while the automated two-session test proves a second lane can finish during a long first-lane call.

`gui_session_disconnect` now uses its target session lane and bound worker. It requires a lease, retires the lease and sticky defaults on success, and clears route facts and the worker on success or an unknown outcome so a later saved connection can reuse the numeric ID. Read-only disconnect removes only the saved connection; closing the SAP window requires write mode. The independent security review found no new authorization bypass in this path. The robustness review found stale route facts and worker lifetime issues, which were fixed and covered by tests.

Explicit attach uses the tray's serial control executor. The dispatcher checks the requested target, refreshes the token immediately before attach, and installs a one-call guard that the handler applies to the live SAP system/client/user and connection name before writing the saved connection. The handler invalidates routed facts as soon as the file changes; the dispatcher verifies the attached session again before returning a result. A failed attach postcheck now detaches the tray COM binding and conditionally deletes only the saved generation written by that attach; commit checks that the generation still exists under the cross-process cache lock. An exception during owner attach also detaches the binding. Owner-mode attach without an explicit session ID stays refused. Owner-mode login reserves the target window's session lane, then holds the admission-probe gate while checking credential identity before typing, refreshing authorization before SAP submission, and verifying the SAP identity after logon. Waiting for a busy login lane no longer holds the global probe gate and so does not block admission to unrelated windows. Owner-mode launch checks the exact newly opened window before a create-only cache write and verifies it again before returning its saved ID. A failed postcheck conditionally removes that saved generation and detaches the tray COM binding. Live MCP launch and subsequent login succeeded on the Bigfox/A4H logon screen, which reports client `000` before authentication and client `001` afterward.

## Proposed execution model

The current implementation keeps one tray process as the HTTP endpoint, authenticator and router, with one bounded serial queue per live SAP session. A private worker process owns each session's COM STA, `CommandHandler`, `ComAutomationEngine` and CLI registry. The local live HTTP probe above confirms useful overlap across SAP GUI windows on this host.

The tray resolves the effective `connection` argument before enqueueing, using explicit argument, server default, token sticky default, then single-connection fallback in the existing order. Every fallback must resolve to a session allowed by the endpoint owner's SAP identity allowlist and the token's narrower rules. It binds the request to an immutable saved connection generation and live session identity. The worker revalidates that identity, current token status and policy, and the live SAP system/client/user immediately before execution. It must fail on mismatch rather than silently reattach. Disconnect uses the bound session lane; explicit attach uses the tray control executor and invalidates saved-connection route facts. Launch and login use the tray control executor and an exclusive admission-probe gate; login also reserves its window's session lane.

Owner-mode `gui_connection_list` now takes a saved-file snapshot without COM validation, then returns only connections whose session ID, server session key, and cache generation match fresh live facts for an allowed SAP identity. It derives the connection name from the live GUI window, removes saved metadata and diagnostics, and applies the token's SAP system and connection-name limits. Cleanup through this MCP listing is refused. The listing has an eight-second aggregate deadline and fails closed if it expires; a single blocking COM probe can still extend wall time beyond that deadline. Owner-mode HTTP `gui_doctor` uses the same bounded verification and reports only the allowed connection count and readiness; the global desktop doctor remains refused for connection-restricted local callers. Credential discovery remains unavailable over owner-mode HTTP.

## State and policy changes

- Keep authentication and server-wide rate limits at the tray. Enforce live session identity, SAP system and transaction allowlists, selection-input restrictions and the read-only guard in the executing worker too. A policy check before enqueue is insufficient when the screen can change while waiting.
- Keep token sticky defaults in the router. Key the transaction-blocked and selection-input initial-screen records by **token ID plus session identity**. Invalidate a record when the session identity or screen changes.
- Retire sticky, transaction-block and initial-screen records on token revocation and session closure. Bound retained state without evicting an active transaction block in a way that would reopen a denied session.
- Add an exclusive session lease for state-changing workflows so another client cannot navigate the same screen between steps. Make an explicit policy decision about write access without a lease; the recommended default is to require one when a session is shared by clients. A screen generation or fingerprint can detect stale assumptions, but must not be treated as a substitute for a lease during multi-step writes.
- A `gui_batch` must hold one session queue slot and any lease for its full duration. Reject mixed-session batches. Specify the behavior of batches that launch or attach a session before implementing them; they cannot be routed as an ordinary already-bound session batch.
- Propagate tray read-only changes and the `FAIRYFLY_READ_ONLY=1` hard cap to every worker. Worker enforcement must use the current effective policy, not only a startup copy.
- For worker processes, use private inherited IPC handles where possible. Authenticate every broker-to-worker request against the broker's current principal and policy; do not expose a worker pipe as an unauthenticated alternate tool endpoint. Keep workers in the same interactive Windows logon session as SAP GUI.
- Centralize audit appends, but obtain actual SAP system, client, user, transaction and outcome from the worker. Preserve the existing semantics of required audit failures, including the possibility that an action already ran before an append failed.

## Failure and cancellation behavior

Each session queue needs its own capacity, fairness and busy response. A pending request can be removed on MCP cancellation or a detected HTTP connection disconnect. The current http.sys disconnect watch is connection-level: an HTTP/2 client that resets one stream while keeping its connection open may not cancel that JSON call promptly. Once a COM action starts, cancellation may only suppress the response; it cannot prove the SAP action stopped. A soft timeout must not free the session for another action while the timed-out COM call is still running.

If a worker exits or is terminated during a state-changing action, return and audit `OUTCOME_UNKNOWN`. Never retry that action automatically. Retire a worker when its session closes, reject its queued calls with a clear session-unavailable result, and create a replacement only after a new identity has been validated. Test whether reading SAP's `Busy` property helps reject calls promptly; do not assume that property itself is always nonblocking.

## Implementation order and acceptance tests

1. **Concurrency spike:** Run the live matrix above and record timings, SAP GUI version and topology. Decide whether threads, processes or serial execution are viable.
2. **Identity and routing:** Create a stable session descriptor with saved connection ID, generation and live identity; validate it before each command. Test closed windows, reused indices, attach/launch races and mismatched SAP system.
3. **Owner identity and client coordination:** Add the configured SAP identity allowlist and filter every listing and action against it. Then add leases, stale-screen detection and session-scoped token policy state. Test disallowed SAP identities, guessed numeric IDs, token-specific restrictions, token rotation/revocation, session closure and ID reuse. For two agents of the same owner, test that a lease prevents one from changing the other's in-progress write workflow.
4. **Per-session executor:** Add routing, bounded queues and one executor per session using the chosen worker form. Prove two different-session calls overlap while same-session calls remain ordered. Verify that shared-resource operations still serialize.
5. **Lifecycle and safety:** Add secure IPC if processes are chosen, centralized audit, read-only propagation, worker recovery, timeout and cancellation mapping. Test worker failure during a write and confirm `OUTCOME_UNKNOWN` with no automatic replay.
6. **Documentation and rollout:** Update [MCP.md](MCP.md), [MCP_REMOTE.md](MCP_REMOTE.md), tray status and integration instructions with the measured concurrency limits and session ownership behavior. Start with an opt-in setting until live two-session tests pass reliably.

The primary acceptance test is end-to-end: one interactive Windows account runs a tray with two SAP GUI sessions logged in as **different SAP users**. Two distinct MCP tokens, each granted one exact SAP identity, discover and operate only their own user's windows. Their calls to different windows overlap, repeated calls to one window remain ordered, and neither token can redirect a queued action to the other SAP user or a closed/reused window. A separate Windows-account probe is an optional deployment isolation test.

## Open decisions

- Repeat the live backend-wait and large-grid measurements across more SAP GUI versions and deployments. The current host showed useful cross-window overlap and uses private workers; the short metadata probe alone did not determine that choice.
- Revisit shared-resource serialization if future routed commands use desktop focus, clipboard, GUI-wide dialogs or external launchers. The current routed commands were audited for those resources.
- Leases are currently mandatory for owner-mode HTTP navigation and writes. Confirm whether the same rule should apply outside owner mode, and retire leases promptly on disconnect and token revocation.
- Whether mixed control-and-session batches should be rejected or supported through an explicit workflow API.
- How to migrate existing endpoints into an owner SAP identity allowlist without unexpectedly denying legitimate sessions on multiple SAP systems or clients.
